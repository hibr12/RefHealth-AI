# Platform integration

The original model artifacts, training scripts, datasets, registry, API contracts and SQLite learning store are retained. The new Node application owns normalized operational and patient data in PostgreSQL. The stateless authenticated bridge reads only the context that Node has authorized and filtered. This avoids duplicating patient or central knowledge tables in Python.

## New bridge routes

All require a configured `CORECARE_API_KEY` and matching `X-API-Key`, even when legacy local-demo endpoints allow unauthenticated development. Never expose this key to the browser.

| Endpoint | Behavior |
|---|---|
| `POST /integration/recommend` | Evaluates supplied registered hospitals, filters unavailable required services/specialties, ranks transparent operational suitability and returns reasons, warnings and timestamps |
| `POST /integration/workload` | Uses verified supplied history and an approved real-data model that supports the hospital; otherwise fails explicitly |
| `POST /integration/assistant` | Retrieves from backend-authorized documents using Gemini embeddings when configured, generates final responses with Groq, returns source IDs/timestamps, and creates unverified proposals |

Recommendations are policy scores, not medical probabilities. Freshness and available capacity take precedence over the numeric score. The score includes capacity, observed workload, distance, queue length, historical acceptance and verified processing time when available. Approved delay and workload models can adjust it; unavailable predictions remain null. Historical aggregates require at least ten observations. Missing evidence is never replaced with synthetic records. Distances are great-circle estimates, not road travel times.

The RefHealth AI Assistant uses `LLM_BASE_URL`, `LLM_API_KEY`, and `LLM_MODEL` for Groq's OpenAI-compatible `/chat/completions` endpoint. Groq generates all final text responses and receives authorized retrieved sources plus recent conversation history. The documented defaults are `https://api.groq.com/openai/v1` and `openai/gpt-oss-20b`. Missing Groq configuration or provider errors produce an explicit 503; the service does not return a fabricated or retrieval-only answer as if it were generated.

`EMBEDDING_BASE_URL`, `EMBEDDING_API_KEY`, and `EMBEDDING_MODEL` configure Gemini `batchEmbedContents` for both question and document embeddings. The query and missing document vectors are batched together, at most 100 inputs per call. Query and document vectors are dimension-checked before cosine similarity. If no Gemini key is configured, retrieval uses explicitly labeled TF-IDF; if Gemini is configured but fails after bounded retries, the request fails explicitly. Citation IDs are checked against retrieved sources.

For the supported `openai/gpt-oss-20b`, `openai/gpt-oss-120b` and `qwen/qwen3.8-27b` models, requests use [Groq strict structured outputs](https://console.groq.com/docs/structured-outputs): a required answer string, source-ID array restricted to current source IDs, and an array of optional operational proposals. Text answers with retrieved context require at least one citation; turns with no sources cannot invent one. Other configured models retain JSON-object mode and local validation. All models remain subject to local answer and citation validation. A malformed optional proposals field is discarded rather than causing a valid cited answer to fail; it cannot create knowledge records.

The backend builds a fresh approved-hospital directory snapshot on every chat request, using the same `APPROVED` visibility boundary as the hospital directory. It contains exact counts, hospital IDs/names/statuses and a timestamp, without contact, capacity or patient fields. Long lists are split into documents below the AI input size limit. Count/list questions and referring follow-ups receive all directory parts alongside relevant retrieved records, so the eight-result similarity limit cannot become an incorrect network total. These snapshots are not embedded or cached. Profile sources also explicitly include hospital status. Here “active” means approved for system access; it does not establish opening hours, referral acceptance or available beds. Pending, rejected and suspended registrations remain outside hospital-user context.

Set `LLM_VISION_MODEL` and `LLM_AUDIO_MODEL` only when authorized Groq vision/transcription models are available. Attachments are not sent to Gemini. Provider keys belong only in the AI service environment, never in the browser. Configure providers only when authorized to receive the hospital information in scope.

## Hospital workspace context

The assistant remains hospital-workspace-only. System administrators do not gain chat access. `backend/src/assistant-context.ts` builds a fresh, role-filtered PostgreSQL snapshot for each request using repeatable-read isolation for its core queries. It includes exact authorized referral totals by status, outgoing/incoming visibility, today's created/updated counts in the application's UTC+03:00 reporting day, verified-outcome counts, saved prediction counts and the latest saved workload forecast. Profiles include opening-hour text, departments, specialties, services, equipment and permitted capacity; private capacity from another hospital is excluded. Missing capacity is unknown, not zero.

Hospital administrators additionally receive their hospital's aggregate membership counts, knowledge-review queue, external-source/job status and twenty recent audit action types/timestamps. Workers get only their existing permissions; a worker without `REFERRAL_RECEIVE` receives no incoming referral details/count, and team administration is excluded. Selecting a Referral ID adds its authorized operational status/history and existing own-hospital predictions, with patient identity, clinical narrative, actor identity, outcome narrative and transition reasons excluded. Staff identities, credentials, hashes, tokens and other users' conversations are never queried for this context. Existing approved knowledge retains its prior authorization rules and review responsibility.

Model context includes the current registry's active model metadata and the same bounded, hospital-scoped verified-outcome metrics available on AI intelligence. Registry failure is explicitly unknown. Active legacy/synthetic models are not represented as validated real-data models; a saved forecast is not an observation or a new prediction. Built-in workflow guidance explains supported actions, roles, account recovery, source collection and media capabilities; chat cannot modify records or train models.

The AI always retains current access boundaries and the own-hospital profile. Other exact workspace snapshots are selected by the question's topic, outside semantic top-eight retrieval. Network facility comparisons retain all supplied authorized profiles; directory counts/lists retain all approved-directory parts. Simple own-hospital questions omit other hospitals' profile context. This reduces unnecessary provider tokens; an initial live attempt with every snapshot on each turn hit Groq HTTP 429. Follow-ups use current snapshots rather than old assistant answers. Broad overview questions include all workspace summary sections. Knowledge content remains limited to the newest 300 authorized approved records, with that limit stated; recent events and performance metrics expose their own bounds.

Fastify checks every returned citation against the documents authorized for that request and reconstructs its content, source name and timestamp from those documents. Unknown citations are rejected before conversation/proposal persistence. This enforces source access and attribution, not a mathematical guarantee that every generated statement is correct. The assistant must acknowledge missing, stale, inaccessible or insufficient evidence instead of inventing an answer. Provider outages and quotas remain explicit failures.

Image turns use the configured vision model and authorized context; an uploaded image is not a verified hospital record. Voice turns use the configured transcription model first, then route the resulting text through the same purpose/retrieval/citation rules as typed messages. MP4/M4A, including browser-produced MP4 audio, is accepted. The AI response adds `transcript` and `user_message` for voice turns. Fastify requires those fields before saving a voice conversation, saves the transcribed user message in the existing private `Conversation.question` field, and never stores raw attachment bytes. Optional typed instructions are retained alongside the transcript. The frontend uses the saved question immediately so follow-ups and reloads keep the spoken content. Provider media contracts follow [Groq vision](https://console.groq.com/docs/vision) and [speech-to-text](https://console.groq.com/docs/speech-to-text) guidance. Browser read-aloud is separate from transcription. It first uses Web Speech and falls back to authenticated `POST /assistant/speech` in Fastify, which looks up the current user/hospital conversation and sends at most 200 characters of its saved answer to service-authenticated `POST /integration/speech`. Neither client-provided text nor another user's conversation can be read through this route. The WAV response is temporary; subsequent segments use the returned offset. Groq defaults to `canopylabs/orpheus-v1-english` / `troy`, overridable with `LLM_SPEECH_MODEL` / `LLM_SPEECH_VOICE`; a non-Groq provider needs an explicit speech model. The organization administrator must accept the speech model terms first. See [Groq speech generation](https://console.groq.com/docs/text-to-speech/orpheus) for the WAV-only, 200-character contract.

Unchanged document vectors use an in-memory LRU cache: at most 512 entries, expiring after 15 minutes. Keys include the requesting hospital, source hospital/document ID, content digest, provider endpoint/model and credential fingerprint. Vectors are never reused across requesting hospitals. The backend supplies the authorized document list on every call, and only those documents can be ranked or cited. Content edits produce a cache miss immediately; changed source metadata is read from the current document. Revoked or removed sources are never restored from the cache. Query vectors and answers are not cached. There is no persistent pgvector index; current context is bounded to 300 knowledge records plus approved hospital profiles.

All assistant provider work shares an 80-second budget. The pooled HTTP client retries transient connection failures and HTTP 408, 429, 500, 502, 503 and 504, up to three attempts per request. Backoff and provider retry delays consume the same budget. Long retry delays, bad credentials, invalid payloads, TLS certificate failures and redirects are returned as explicit failures. Logs include only provider hostname, attempt count and error category. The backend's `AI_ASSISTANT_TIMEOUT_MS` defaults to 90,000 (allowed range 85,000–95,000); the frontend and assistant Nginx route allow 100 seconds. No whole-chat POST is automatically replayed by the frontend or backend. Connection reuse follows the [HTTPX client guidance](https://www.python-httpx.org/advanced/clients/), and status handling follows the [Groq error reference](https://console.groq.com/docs/errors).

Messages accept 1–2,000 non-whitespace characters after trimming. Simple greetings and recognized complete questions about the assistant's identity, purpose, capabilities or limitations skip hospital retrieval and still receive a Groq-generated reply. These explanations use the application description in the system prompt and return no hospital citations. Routing uses conservative full-question matches, including conversational prefixes such as “ok”; mixed or unmatched questions and all attachments retain normal retrieval. Provider output cannot select this exemption. Hospital answers with retrieved context still require citations, and unknown source IDs are rejected for every answer. Audio is transcribed before its single retrieval pass; optional image/audio processing remains separate from the prediction models.

## Verified learning bridge

Set `PLATFORM_BACKEND_URL` and run:

```bash
python -m training.import_platform_observations
python -m training.learning_cycle
```

The importer reads `/internal/learning-export` using service authentication. The export contains only verified daily observations and completed referrals with verified outcomes and prospectively saved operational features. It excludes patient identity and clinical narrative. Referrals missing fresh, explicitly shared operational evidence are excluded from delay training; later data is never used to reconstruct earlier features. Acknowledgement time derives from the receiving hospital's status history.

The importer deduplicates by stable platform source references, validates timestamps, and fails on conflicting records. Run one importer/learning worker at a time. Learning still requires sufficient representative data, chronological evaluation, comparison and explicit model approval. Importing data does not train or activate a model. The existing rollback and promotion commands remain unchanged.

## Evidence limitations

The supplied V6 candidate fails its activation gate. The referral dataset has only 15 synthetic rows. No clinically validated real-data model was supplied, so real-platform predictions cannot honestly be demonstrated as available. Software tests exercise actual legacy models in isolated synthetic workflows; platform tests exercise honest operational ranking and failure handling. Obtain verified representative hospital data and professional acceptance before model activation.
